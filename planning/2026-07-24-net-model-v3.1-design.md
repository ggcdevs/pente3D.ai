## 1. Why (the synthesis)

Every networked-game bug in v3 traces to ONE thing #35's durability mechanism introduced:
`net-room:{code}` — a **locally-persisted game+seatmap keyed by the room CODE** — which quietly did
two harmful things:

1. **Re-coupled code↔game.** The rendezvous code became bound to a saved game, resurrecting stale
   games (#43 single-browser; #46 networked, where the stale game is pushed to the peer).
2. **Became a stale local substitute for real state-sync.** On (re)connect a peer resumes from its
   local snapshot instead of converging to the authoritative LIVE state, so a peer that missed moves
   stays behind (#45) — and acting on stale state diverges/bricks the game.

The whole cluster is these two roots wearing five masks: #40 (stale seatmap), #42 (non-shared
identity), #43/#46 (code↔game), #45 (stale snapshot instead of live resync).

## 2. Principles (the design direction)

- **A. Identity = UUID, fully decoupled from code.** A code is *pure rendezvous* (find the peer),
  reusable, identifying no game. Games are stored by **UUID** (the archive already does). A room
  remembers at most a lightweight **reconnect pointer** — `{ gameUuid, mySeat }` — NEVER a full
  game snapshot that gets *adopted*.
- **B. On (re)connect, converge to the authoritative LIVE state — never resume from a local snapshot.**
  Missed moves get caught up, not lost. (Mechanism = OPEN Q1.)
- **C. Enforce seed-proposal semantics on the WIRE.**
  - `New` → publish/accept ONLY empty state; **reject** received non-empty.
  - `Resume`/`Current` → publish own concrete game; reject a *different* concrete game.
  - `Dealer's Choice` (defer) → the ONLY kind that adopts the peer's non-empty state.

## 3. Open questions (the brainstorm)

- **Q1 — Live-state resync mechanism (linchpin for #45).** Options:
  - (a) **Retained current-state message per room on the relay** (MQTT `retain`): any (re)joining
    peer immediately receives the latest authoritative game. Simple, works even if the other peer is
    momentarily absent; cost = retained-message lifecycle/cleanup, and the relay holds game state
    (tension with "dumb relay").
  - (b) **Resident-peer republishes full state on presence** (a peer joins → the present peer re-sends
    its current log). Keeps the relay dumb; fails if BOTH peers were absent (empty room = nobody to
    republish → falls back to the reconnect pointer + archive).
  - (c) **Hybrid:** retained pointer/headHash on the relay + peer republish of the full log.
- **Q2 — What does `net-room:{code}` become?** A minimal reconnect pointer (`{gameUuid, mySeat, epoch?}`)
  vs. keeping a snapshot but never auto-adopting it. Interaction with the archive (games by UUID).
- **Q3 — How does resync interact with #35's admission/reconciliation?** Does the retained/republished
  live state supersede admission's game-sharing, or feed into `reconcile`?
- **Q4 — Wire enforcement point.** Admission messages already carry a proposal; where does the receiver
  validate "New must be empty / reject non-empty" — in `admission.ts reconcile`, or a new guard?
- **Q5 — Migration/back-compat.** Existing `net-room:{code}` localStorage records on real devices.
- **Q6 — Divergence UX.** #45's "Undo on stale state → diverged → bricked" — once resync is correct,
  should genuine divergence still hard-stop, or offer resync/rewind (ties to #38)?

## 4. Testing strategy (hook)

The repo now has a **scriptable CLI net client** (`cli/`, play daemon + wait/move verbs) — ideal for
deterministic cross-"device" scenarios the browser-only tests can't easily drive: **the #45 repro**
(peer A offline, B moves, A reconnects → must catch up), rematch+reconnect, code-reuse New-Game, and
the two-peers-both-drop case. Pair CLI-vs-CLI and CLI-vs-browser over the real relay.
