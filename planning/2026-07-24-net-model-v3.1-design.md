# Networked Game Model — v3.1 Remodel

**Status:** Design agreed with the user 2026-07-24/25. Ready to plan implementation.
**Branch:** `feat/net-model-v3.1` (playable at `/feat/net-model-v3.1/` via the generalized deploy).
**Epic:** #47 · **Milestone:** v3.1
**Absorbs/supersedes:** #40, #42, #43, #38 · **Directly fixes:** #45, #46

---

## 1. Why — the root cause

Every networked-game bug in v3 traces to one thing #35's durability mechanism introduced:
`net-room:{code}` — a **game + seatmap persisted per room CODE**. That single decision did two
harmful things:

1. **Re-coupled code↔game.** The rendezvous code became bound to a saved game, resurrecting stale
   games (#43 single-browser; #46 networked, where the stale game is *pushed to the peer*).
2. **Became a stale local substitute for real state-sync.** On (re)connect a peer resumed from its
   local snapshot instead of converging to the authoritative LIVE state, so a peer that missed moves
   stayed behind (#45) — and acting on stale state diverged and bricked the game.

Five bugs, two roots: #40 (stale seatmap), #42 (non-shared identity), #43/#46 (code↔game),
#45 (stale snapshot instead of live resync).

## 2. The model

> **A room code is pure rendezvous. A game is a UUID. There is NO mapping between them, anywhere.**

Where state lives — and nothing else:

| Where | What | Notes |
|---|---|---|
| **localStorage** | `visitedRoomCodes: string[]` | The dropdown's memory. Codes only. Already exists (`recentCodes`). |
| **localStorage** | `activeNetworkedGame: { code, gameUuid, updatedAt } \| null` | **Session breadcrumb**, purely for tab-reload. Cleared when the game completes. |
| **IndexedDB (archive)** | games keyed by **UUID** | The source of truth for game bytes. Includes the identity-owned seatmap. |
| **JS memory** | the loaded game + live session | `activeGame` is a runtime var — **not** persisted. |

**Deleted:** `net-room:{code}` and every code→game lookup.

Rationale (user): *"there should also be a pointer like `activeGame`: UUID<str>. that's it lmao. no
link between the two."* And on reuse: *"i would love to be able to just tell my buddy 'hey, jump on
DUDEEE and let's play', and we just keep re-using that for all of our games."* A code accumulates a
*history* of games; it never owns one.

### The breadcrumb invariant (write this down so nobody "generalizes" it later)

`activeNetworkedGame` is **session state** ("I am *currently mid-game* in room X as game Y"), not a
**mapping** ("room X owns game Y"). It is cleared on completion and drives a **prompt, never an
auto-load** — so it can only ever point at a genuinely in-progress game. It is **never published**.
Dual-tracked: localStorage for reload recovery, a JS var for the live session (the JS var survives a
win so the rematch flow works; localStorage is re-set only on mutual rematch).

## 3. Entry resolution — explicit selection, enforced on the wire

Entering a room, you pick a **seed**: **New** · **Resume** (from your games list) · **Current local
board** · **Dealer's choice** (defer). Enforcement (user, issue #46): *"when selecting 'New Game', i
would expect the laptop to never send non-empty gamestate data and i would expect my phone to reject
any non-empty gamestate data. only 'Dealer's Choice' should allow a device to accept non-empty
gamestate data from the other device."*

| Seed | Sends | Accepts |
|---|---|---|
| **New** | empty only (fresh UUID) | empty only — **reject** non-empty |
| **Resume** / **Current** | its own concrete game | the SAME uuid only — reject a different concrete game |
| **Dealer's choice** | nothing | **the only kind that adopts a peer's non-empty game** |

Mismatched seeds (e.g. New vs Current) → **honest typed rejection**, not silent adoption:
*"if i choose 'new game', but the other user chose to start with loading their local board... we
can't play; it throws an error because i opted for a new game."*

**Both pick New** → both are empty and interchangeable → deterministically adopt ONE uuid via
initiator election (earlier arrival, then lower `playerId`). This is the proper fix for **#42** —
a genuinely shared UUID at genesis, not "converges on the first move."

## 4. Live-state convergence — resident-peer republish (fixes #45)

**Chosen over retained MQTT state**, deliberately: a retained per-room message would re-couple
code↔game *at the broker* (the topic would own a game), destroying the "reuse DUDEEE forever" model.
Resident-peer republish keeps the relay dumb and the code pure rendezvous.

- **On presence** (a peer appears — hook `PresenceTracker`), the resident peer **republishes its full
  authoritative log**. Idempotent; the returning peer converges. This is the #45 fix.
- **Both absent** (empty room): the returning peer loads its own game from the archive by UUID and
  waits; convergence happens when the other returns.
- Proposals stay **non-retained + id-deduped** (#35's rule — no stale proposal replay).

## 5. Reconciliation — one narrow auto path, everything else explicit

**Key property:** the turn gate caps *legitimate* drift at **exactly one move**. If it's your turn
and you're offline they cannot move; if it's their turn they move once and are then blocked. Undo
requires mutual confirm. Therefore **any divergence beyond one move is already anomalous** and must
not be auto-adopted.

1. **Identical** (`headHash` equal) → play on.
2. **Auto fast-forward — the ONE automatic case:** your log says it was *their* turn, and their log
   is **exactly one move** longer with your log as its prefix → **adopt automatically**. This is the
   common, expected case: *"they should be able to at least reasonably play their turn while you step
   away, turn your phone off, whatever... in fact, that's probably common."* (Mirror case: you are one
   ahead because your move never published → you republish, they FF.)
3. **Everything else** (longer prefix, or a genuine fork) → **no auto-adopt**. Find the **last common
   ancestor** (walk both hash chains back to the last matching hash — free, by construction), render a
   **pretty-printed diff**, and let the players **choose a resolution via handshake**. Built upfront,
   not deferred: *"if i know imma want LCA + diff + handshake on the agreed resolution, then let's
   build it upfront so that we don't have to redesign again."* (This absorbs **#38**.)

### Integrity — the threat model

A dumb relay **cannot** referee: retained messages are written by clients, and `relay.json` ships a
single shared credential, so the broker cannot even distinguish the two players. Real anti-cheat needs
an authoritative server running the rules engine — out of scope (see §9).

What we do instead, and it is sufficient for friendly play:
- The **hash chain** makes silent history rewriting impossible — any edit changes `headHash`.
- **Validate an adopted log by replaying it through the pure rules engine** (`placePiece` fold) rather
  than trusting the sender's derived state; reject on any illegal entry.
- With two players, **the opponent's client is the validator**, and it has no incentive to accept a
  bogus log. The only surviving cheat requires *both* clients to be modified.

## 6. Reload & rejoin flow

**A tab reload always lands on an empty slate** — no auto-resume of `activeGame`
(*"if you restart (i.e.: reload the tab), you should always get dropped back to the main page with an
empty slate/board"*). Games are never lost: they are durable in the archive by UUID, reachable from
the games list.

If the `activeNetworkedGame` breadcrumb exists, **probe the room on load** (connect, check presence,
and compare the waiting peer's game UUID from its `hello`):

| Probe result | Offer |
|---|---|
| Peer present, **same** game uuid | "Rejoin DUDEEE as **Black**?" (color **derived** from the game's seatmap — see §7) |
| Peer present, **different** game uuid | Warn — do not hijack: *"Do you want to restart your last DUDEEE game with a new code?"* |
| Room empty | "You were playing DUDEEE, but no one is there anymore. Rejoin as Black anyway?" (rejoin and wait) |

Declining clears the breadcrumb; `updatedAt` lets a long-stale breadcrumb expire quietly. If the game
ended while you were away, you rejoin, adopt their state, see the result, and the breadcrumb clears —
the flow self-heals.

## 7. Seats — unchanged from #35

Seats stay **identity-owned on the game** (`{white,black}` = `playerId`), reclaimed by identity. The
rejoin prompt **displays** your derived color; it does not negotiate one — that is what prevents
reopening #31 (both players Black) and #40 (wrong color after a rematch swap). An explicit colour
*preference* for **new** games is a separate nicety (its own ticket), resolved by election on a tie.

## 8. Testing strategy

- **The `cli/` net client is the lever.** It scripts deterministic cross-"device" scenarios the browser
  can't easily drive: the **#45 repro** (A offline → B moves → A returns → must catch up), rematch +
  reconnect, code-reuse New-Game (#46), both-absent return, and the FF-vs-diff boundary (1 move = auto,
  2 = diff). Run CLI-vs-CLI and CLI-vs-browser over the real relay.
- Pure logic (reconciliation decision, LCA, seed/wire rules, election) → unit + fast-check + mutation.
- Glue (republish-on-presence, probe, prompts) → Playwright two-context.
- Every gate must be proven to bite.

## 9. Out of scope / future

- **Authoritative server** (real anti-cheat + server-side state): a v4-scale change — backend, hosting,
  and it dissolves the peer-to-peer model. Captured as an option, not planned.
- Colour preference on **new** games (separate ticket).
- #34 randomized board, #36 spectator, #37 games list — revisit against this model.

## 10. Ticket disposition

**Decision (user, 2026-07-25): leave the v3 tickets where they are and re-review at the END of v3.1.**
Rationale, verbatim: *"behavior makes it in, any previously considered wiring does not. i might just
leave them and plan a re-review at the end to see what's still needed behavior-wise."* Since every
implementation is being rebuilt, pre-sorting tickets by their old wiring is churn; what matters is
which *behaviours* still need to exist once the remodel lands.

Already in v3.1 (the remodel itself): #47 (epic), #45, #46, #43, #42, #38, #49.

**Closing re-review checklist** — for each, ask "is this behaviour still required, and does it still
hold?": #40 (rematch→reconnect keeps the swapped colour), #31 (two Joiners get distinct seats),
#41 (real-relay scenario matrix — scenarios themselves change), #33 (networked history slider),
#34 (random seed — now just another seed kind), #36 (spectator — re-spec against §3).

⚠️ **#37 (games list / resume UI) is different in kind** — not previously-considered wiring, but a
behaviour gap this design *creates*: with reload→empty slate (§6) and no code→game mapping (§2), the
games list becomes the ONLY route back to a game.
**Decision (user, 2026-07-25): IN SCOPE for v3.1** — *"agreed on 37. we do already have some of that,
but whatever extension you think it needs for 3.1 let's build."* Build on the existing archive widget
rather than starting fresh; scope the extension to what the model requires (browse finished +
unfinished, resume by UUID, seed the Resume selector).

## 11. Release decision

**v3 never ships standalone; v3.1 is what reaches `main`.** *(User, 2026-07-25: "leave main, let 3.1
be what ships.")* Rationale: v3 is feature-rich but carries the game-bricking #45 and the stale-game
push #46; shipping it would hand friends the exact bugs this remodel exists to remove. The ~16
completed v3 tickets therefore close together when v3.1 merges to `main`. `dev` remains the playable
integration branch; `/feat/net-model-v3.1/` is the remodel's environment.
