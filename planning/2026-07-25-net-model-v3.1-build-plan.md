## V.0 — The repro, first · **DONE** (`0aada30`, `e425994`)

The bug that froze v3 now has a deterministic failing test **before** any net code moves, as the
handoff required.

- `cli/netlink.ts` — the mqtt.js connect seam plus a controllable link: `pente drop` kills the socket
  (`reconnectPeriod = 0` + destroy the stream, so the broker's Last-Will fires) under a session that
  keeps its engine/seat/game and still reports `phase: connected`; `pente restore` reconnects. That
  session-vs-transport split is where #45 lives. `--json` on every state verb feeds scripts.
- `cli/scenarios/harness.ts` — each peer is a real `pente play` daemon in its own process with its own
  state dir, identity and DB; two clients that meet only at the broker. Assertions read the daemon's
  own snapshot (proof-by-state).
- `npm run scenario:issue45` — the report replayed verbatim. **Identical on two runs:**

```
✗ phone CAUGHT UP to the live game (ply 2) — ply=1 (laptop=2)
✗ phone's board holds the move made while it was away — pieces[1,1,1]=undefined
✗ phone knows it is ITS turn again — canPlace=false turn=black
✗ the game is not deadlocked — phone.canPlace=false laptop.canPlace=false
✗ phone can still play after reconnecting — move REFUSED
```

Both peers online, both seeing each other present, each waiting on the other, white unable to ever
move: the "bricked" game, mechanised. **This scenario going green is the acceptance test for V.3.**

### What the repro also established (facts the plan depends on)

1. **The presence edge exists on the real relay.** The resident observed the returning peer go
   `absent` (Last-Will) and then `present` again — so "republish on presence" has a real hook.
2. **The suppression risk is real too.** `MqttTransport.acked` dedupes the live-presence ack per peer
   and `PresenceTracker` only notifies when the live SET changes. Absence is what resets both
   (`acked.delete(id)` on an empty body). A blip the broker never turns into an absence therefore
   yields **no** presence transition — so the republish trigger must not depend on an absence having
   been observed (see V.3 guardrail).

   > **Superseded by V.3 (review follow-up).** The un-gated trigger alone fixed only the RESIDENT
   > direction: with the ack latched, a returner the broker never declared absent received no live
   > signal at all and so never republished — §5's mirror was unreachable in exactly the case the
   > design names. The `acked` latch is gone; the ack now answers EVERY announce and is marked
   > `ack: true` so an ack is never answered back (that flag, not a latch, terminates the exchange).
   > Driven both ways against the real relay by `npm run scenario:mirror` (a silent, lossy outage:
   > no Last-Will, and the move made while down is discarded rather than queued), and it reports the
   > mirror deadlock when the latch is put back.
   >
   > **Second follow-up — the mirror needed more than a trigger.** That claim of "green" was measured
   > over too few runs: review found the mirror failing ~10% of ~35 real-relay runs, with the failure
   > mode being #45 itself (both peers online, each waiting on the other). The cause was structural,
   > not flaky — convergence rested on ONE unacknowledged QoS-0 publish fired by the returner's own
   > re-announce, with no retry, no ack, and no arm in `decideSync` by which the peer that is AHEAD
   > answers. Lose that single message and the pair is bricked forever. `SyncEngine.receive` now
   > ANSWERS a peer that is behind (design §5 "I am ahead → republish"), which turns a one-shot push
   > into a converging exchange: every publish by the behind peer draws our longer log. Silent on an
   > equal log, so it terminates. Re-measured: **12/12 green** where the same suite failed ~10%.
3. **Nothing re-runs admission on an mqtt.js auto-reconnect.** The transport re-subscribes and
   re-announces presence; `NetSession` never re-`enter`s, so no `hello` → no `admit` → no state. The
   missed move was published non-retained and is simply gone.

## Net-layer map (current, from investigation)

- **`net-room:{code}`** (`session.ts` `roomStateId`/`loadRoomState`/`persistRoomState`, archive marker
  `NET_ROOM_RESULT`) is the root to delete: a game + seat map persisted per room **code**, written on
  establish/admit/arbitrate/rematch and re-loaded by `buildProvisionalSeat` for a `defer` entry.
- **Sync policy** is `decideSync` (`sync.ts:527`) — today it adopts **any** strict extension, however
  many moves ahead. V.3.1's narrow one-move rule replaces exactly this. `decideSyncEpoched` layers
  the rematch generation on top and stays.
- **`SyncEngine.publishState()`** (`sync.ts:981`) already publishes the full log — the primitive
  resident-peer republish needs; no new message kind.
- **Admission** (`admission.ts` `reconcile`/`electInitiator`, message codec + `AdmissionDeduper` in
  `sync.ts`, driven by `NetSession.enter`) is the right shape; the seed matrix is what changes.
- **Seats** are identity-owned on the game (`seats.ts`, `PersistedSeats`) — keep, do not touch.
- **`recentCodes.ts`** (`pente:recentCodes`, injected `Storage`) is already the design's
  `visitedRoomCodes`; reuse it rather than adding a second store.
- **`main.ts`** restores `AUTOSAVE_ID_KEY` on boot — that is the auto-resume §6 forbids.
- **`archive.ts`** has `loadNetGameByUuid` + `listArchivedGames` (which filters the room-state
  records out) — the UUID-keyed base for #37; the filter dies with the marker.

## Guardrails (landmines — each one is a bug we already paid for)

- **Never re-introduce a code→game mapping.** Not in localStorage, not in the archive, and *not as a
  retained MQTT message* — retained state would re-couple code↔game at the broker and kill the
  "re-use DUDEEE forever" model the whole design exists to serve (§4).
- **The breadcrumb is session state, not a mapping.** `activeNetworkedGame` drives a **prompt, never
  an auto-load**, is cleared on completion, and is **never published** (§2).
- **Auto-adopt is ONLY the one-move fast-forward.** Any longer prefix or any fork goes to LCA + diff +
  handshake. The turn gate caps *legitimate* drift at one move, so anything more is already anomalous.
- **Validate an adopted log by REPLAYING it** through the pure rules engine; never trust a sender's
  derived state. Reject on the first illegal entry, honestly.
- **A dumb relay cannot referee** (one shared credential; retained messages are client-written). The
  hash chain + replay-validation + "the opponent's client is the validator" is the threat model. An
  authoritative server is #50, not this build.
- **Rejoin DISPLAYS a derived colour; it never negotiates one** — that is what keeps #31 and #40 shut.
- Admission stays **non-retained + id-deduped**; a reconnect must never replay a stale proposal.
- `randomId.ts`, never `crypto.randomUUID` — the latter is `undefined` over plain-LAN http and
  Playwright (always a secure context) will not catch it.
- Cross-component wiring gets its own test. #35 passed every component gate at 98% mutation while the
  durable seat map was silently not wired.

## Decisions taken mid-build

### One record per game — key every autosave by `game.uuid`, retire `autosaveId`

- **Status:** Accepted (2026-07-25). Assigned to **V.5**, which already rewrites the boot/restore path
  that owns `AUTOSAVE_ID_KEY`. V.6 must inherit one record per game, not a listing heuristic.
- **Context:** V.1 deleted `persistRoomState`, the only writer of the identity-owned seat map, so the
  session began archiving the authoritative game under its **own uuid** (design §2 "games keyed by
  UUID"). That collided with `main.ts`'s autosave writing the same game under the app's `autosaveId`
  → two archive records for one networked game. Two e2e tests caught it. V.1's fix made the two
  writers *cooperate*: a shared `playersFromSeats` projection, `archivedStartedAts` priming so both
  agree on the date, and a **shadow-collapse rule** in `listArchivedGames` that hides the
  non-canonical copy. It works, and every piece of it exists only because one game has two records.
- **Rationale:** since #35/S.1 **every `Game` already carries a uuid**, so keying every autosave
  record by `game.uuid` — local games included — makes one game have exactly one record by
  construction, and the cooperation machinery deletes. The reviewer-found `autosaveMeta` bug (one
  metadata object gated on two different predicates, so a post-conflict local record took the
  conflicted net game's date) was a symptom of the same double-write. Expect a net removal of code.
  User, asked whether to keep the arrangement or remove it: *"yeah, no, remoing that machinery seems
  good :)"*
- **Constraint:** the re-keying must be a migration, not a loss — records already stored under an old
  autosave id carry `meta.uuid` and must stay listed and resumable.

### The seed matrix is enforced on THREE channels, and `admit` can name the newcomer's game

- **Status:** Accepted (2026-07-25), landed in **V.2** (round 2, from V.2's review findings).
- **Context:** V.2 round 1 enforced the matrix on the admission channel only, and composed the arbiter's
  verdict inline in `session.ts` as `reconcile` → "can I serve the agreed game?" → `acceptsGame`. Two
  consequences the reviewer proved with probes on two real `NetSession`s: (a) the matrix's *only*
  adopting row — "dealer's choice is the ONLY kind that adopts a peer's non-empty game" — was
  **unreachable whenever the deferrer was the arbiter**, because an arbiter can serve nothing but its own
  engine, so the honesty guard refused the newcomer's game as `game-mismatch` (a game the deferrer never
  proposed); and (b) the **move-sync channel had no seed gate at all**, so any peer whose log was
  momentarily empty adopted a foreign non-empty game wholesale — the user's #46 rule broken on the one
  channel admission never inspects, reachable with an ordinary `kind:'sync'` publish.
- **Rationale:** the fix is structural, not a patch per symptom. The arbiter's verdict moves into the
  pure, mutation-gated `decideAdmission(mySeed, gameIHold, theirSeed)` so the wire has one rule (and the
  fast-check property now tests that rule instead of a model of it — the round-1 property excluded
  `defer` and assumed each peer serves the game it *declared*, which is not what the wire does). `admit`
  gains a tagged `agreed` field so a deferring arbiter can name the **newcomer's** game instead of
  serving one it does not have. And `acceptsGame` is applied on the sync channel to any log belonging to
  a *different* game — the seed only ever governs adopting a game you are not already on, so same-game
  convergence is untouched.
- **Consequence — the rematch game's uuid is now DERIVED** (`rematchGameUuid`): with a seed gate on the
  sync channel, a rematch could no longer rely on two independently-minted empty games merging by the
  log-prefix accident (a `new`-seeded host would refuse the peer's first move). Deriving the fresh id
  from the prior uuid + the new generation — facts both peers already share — makes a rematch ONE game at
  genesis, and incidentally stops it archiving two records.
- **Also:** a `resume`/`current` seed naming a game this browser does not hold now refuses
  `seed-unavailable` instead of degrading to a fresh game while still announcing the named one. The
  degrade put a claim on the wire it could not honour, and the downstream refusal it caused was
  mislabelled `game-mismatch` — "you and the other player brought different games" when both had brought
  the same one.

### V.4 is split: V.4a (pure decision) then V.4b (handshake + panel)

- **Status:** Accepted (2026-07-25), before V.4a was built. V.4a landed at `f3bea6c`; **V.4b is the
  next task and closes the window below.**
- **Context:** V.4 was the largest task in the plan (~30k) and the one where a single agent was most
  likely to hand back something plausible-but-wrong. Asked whether to split it, the user: *"split is
  good."* V.4a is the pure half — the narrow fast-forward decision, the last-common-ancestor walk,
  the diff, and replay-validation, all mutation-gated. V.4b is the protocol and UI half: the
  resolution handshake reusing the N.1 primitive, and the divergence panel.
- **⚠️ Interim window this creates, recorded because it is a real regression while it lasts.**
  Between V.4a and V.4b a divergence beyond one move is *detected* (`SyncEngine.needsResolution()`)
  but has no consumer: no session accessor, no `window.__pente` hook, no UI, no CLI scenario. So the
  pair silently stops converging, the player is not told, and the next local move turns it into a
  genuine fork that permanently stops and conflict-archives the game. v3 auto-adopted this case, so
  **both** of those outcomes are new. Nothing ships in this state — V.4b is the immediately following
  task on the same branch, and the design's own words are *"if i know imma want LCA + diff +
  handshake on the agreed resolution, then let's build it upfront so that we don't have to redesign
  again"* — but a reader of this plan should not have to infer the gap from a code TODO.
- **CLOSED by V.4b.** Session accessors (`divergenceFacts`/`divergenceView`/`proposeResolution`/
  `respondResolution`/`applyAcceptedResolution`), the `window.__pente.getDivergence` hook, the
  `divergencePanel` widget over the pure `ui/widgets/divergenceModel.ts`, the CLI (`divergence` on
  every snapshot + `pente resolve|agree|refuse`), a two-client Playwright spec (`e2e/divergence.spec.ts`)
  and a real-relay CLI scenario (`npm run scenario:divergence`). A fork still STOPS the game — playing
  on an unsettled split is what deepens it — but it is no longer a **terminus**: an agreed resolution
  lifts the stop (`SyncEngine.applyResolution` → `settleDivergence`), and the conflicted archive
  record is deliberately kept so agreeing to the other history never destroys your own.

### The detecting side ANSWERS, so a divergence is mutual

- **Status:** Accepted (2026-07-25), landed in **V.4b**.
- **Context:** V.4a's `needs-resolution` arm was silent, and `decideSync` answers a peer that is at
  most ONE behind. So a peer two or more behind published its short log, got nothing back, and went
  on rendering an ordinary board — the divergence was visible only to the side that was *ahead*,
  i.e. to everyone except the player who was actually missing moves.
- **Rationale:** the answer is `publishState()`, not a new message kind: a divergence is a fact about
  two logs, and the log is the thing that carries it. The peer then runs the same policy on the same
  pair and reaches the same arm, so both panels open and either player may propose.

  > **Review follow-up — the answer needed a retry, not a latch.** As first landed the answer went out
  > EXACTLY ONCE per `myHead|theirHead` pair, which is the shape of the `acked` latch V.3 deleted for
  > this very reason: nothing acks a QoS-0 publish and nothing re-sends it, so one dropped packet left
  > the peer that is MISSING MOVES uninformed forever — it kept rendering an ordinary board and played
  > on, deepening a one-sided divergence into a genuine fork. The latch is gone. EVERY announce is now
  > answered, and the log published as an answer carries `tag: 'answering'`; no arm ever answers a
  > tagged answer, and that — the same flag-not-a-latch shape the presence ack uses — is what
  > terminates the exchange. The peer's own re-announce (presence republish / resync / reconnect) is
  > therefore the retry. Pinned by `sync.test.ts`'s LOSSY echoing relay, which drops every answer and
  > asserts the behind peer is still told on the next announce (the test fails if the latch is put
  > back).
  >
  > Answering every announce has one consequence worth naming: the side that resolves FIRST gets its
  > (correct, still-diverged) pre-resolution log answered back, which re-opens the record it just
  > closed. `applyResolution` therefore publishes with `tag: 'settled'`, and an identical history
  > arriving so tagged drops any record the receiver holds — safe against the echo, because if it is
  > our own message coming back we had already dropped the record before publishing it.

### A resolution names a HEAD HASH, not a side

- **Status:** Accepted (2026-07-25), landed in **V.4b** (`src/net/resolution.ts`).
- **Context:** the obvious wire encoding is proposer-relative (`take-mine`/`take-theirs`), which the
  responder must invert. That inversion is only correct while the two peers' divergence records are
  exact mirrors, and on a publicly-writable relay a third publisher can put a log in the room that
  BOTH peers record as `theirs` — where the inversion lands them on *different* histories while both
  believe they agreed.
- **Rationale:** `resolve:<headHash>` names the target absolutely. The head hash already fingerprints
  identity + whole history, so the receiver answers "is that mine, theirs, or the ancestor?" with one
  comparison — and can say honestly that it is **none of them** rather than guess, which is what makes
  `canAccept: false` (decline-only) a reachable, honest state instead of a silent mis-adoption.

### The live relay ECHOES a client's own publishes back to it

- **Status:** Discovered while building **V.4b**; recorded because it invalidates a natural assumption
  and is not visible from any mock-transport test.
- **Context:** MQTT 3.1.1 has no `noLocal`, and the deployed broker was probed directly (subscribe →
  publish → the message arrives back). `MockRelayHub` deliberately does NOT echo ("faithful relay:
  never echo to the sender"), so the entire unit suite was green while the real-relay CLI scenario
  ping-ponged forever and the divergence panel flickered out from under the player.
- **Consequence (both fixed in V.4b):** (a) the `in-sync` arm may not treat "a log identical to mine"
  as "the peer agreed again" — that message is nearly always *our own*, and clearing the divergence
  record on it deleted the record moments after it was made; a peer that genuinely converges moves
  OUR head too, which `emitChange`'s `divergenceIsOver` already catches. (b) The answer-terminator
  cannot be keyed on the divergence record (the echo wipes it) — and, per the review follow-up above,
  must not be a per-head-pair latch either, because a latch cannot retry a lost answer. It is a TAG on
  the answer itself (`tag: 'answering'`), which no arm answers back. Both are pinned by
  `sync.test.ts`'s ECHOING-relay transport, a faithful model of the broker, now with a drop hook that
  models QoS-0 loss.

### The divergence panel is a full-viewport overlay, so its zone may not be `transform`ed

- **Status:** Accepted (2026-07-26), fixing a review blocker on **V.4b**.
- **Context:** the panel shipped rendering as a 24x24 box: `.pente-divergence` is
  `position: fixed; inset: 0`, but `.pente-ui-zone--center` carried `transform: translate(-50%,-50%)`,
  and a transformed element is the CONTAINING BLOCK for its fixed descendants. `inset: 0` therefore
  resolved to the zone's 24x24 padding box (every centre widget is out of flow, so the zone has no
  size of its own), the card collapsed to a 174px column wrapping one word per line, and the headline
  sat above `y = 0`. `endStateOverlay` inherits the same shape and was only saved by being short.
- **Rationale:** the centre zone now spans the overlay and centres with flexbox — no transform, no
  containing block, `fixed` means the viewport again — and both cards carry viewport `max-width` /
  `max-height` + `overflow-y: auto` so no card can outgrow the screen. Rendering is not something a
  `toBeVisible()` can prove (a 24x24 box is "visible"): `e2e/divergence.spec.ts` MEASURES the card,
  the headline and every button against the viewport, in the one-sided, incoming-ask, waiting and
  FORK states, and lands the screenshots in `e2e/artifacts/` where the visual review looks. The
  measurement was watched rejecting the old CSS (card width 48px < 340px floor).

### A wait for the peer must keep its buttons; an ask with no divergence must stay answerable

- **Status:** Accepted (2026-07-26), fixing a review finding on **V.4b**.
- **Context:** V.4b replaced one dead end (a fork) with two smaller ones. While our ask was pending
  the card showed no options at all — no withdraw, no re-ask, no timeout — so a lost ask left the
  proposer watching "Waiting for your opponent to agree…" forever. And an incoming `resolve:` ask that
  reached a client holding NO divergence rendered the fully hidden card, so that player could neither
  see nor refuse it; only `session.respondResolution(false)` from the console could.
- **Rationale:** the options stay on screen while waiting — re-picking supersedes our own ask (the
  handshake's at-most-one rule, which supersedes on the peer's side too), so the same choice re-sends
  a lost ask and a different one changes our mind. A local-only withdraw is deliberately NOT offered:
  it would leave the peer holding an ask we had stopped listening for, a worse dead end than the one
  it fixes. The stranded ask now renders the same decline-only card an unmatchable target gets — there
  is genuinely nothing to accept, and the honest answer has to be reachable.

### Known limitation: two players suggesting a resolution at the SAME moment

- **Status:** Recorded, not fixed, in **V.4b**. A collaboration point for the user (the panel copy /
  flow is already one).
- **Context:** the shared N.1 primitive holds AT MOST ONE pending proposal and "the latest ask wins"
  — a rule #12 and #18 have always had. If both players click a resolution inside one relay
  round-trip, each peer's outgoing ask is superseded by the other's incoming one, and if both then
  agree, each applies the effect the OTHER named: they SWAP histories and are still apart.
- **Why it is left:** nothing is lost or corrupted — both histories still exist on both sides, the
  divergence is immediately re-detected and re-announced (the answer arm), and the pair can simply
  resolve again, which succeeds as soon as one side answers before the other asks. Fixing it properly
  means a deterministic tie-break in the SHARED handshake (e.g. the lower proposal id wins a
  collision instead of the later one), which changes behaviour for #12/#18 as well — a decision for
  the user, not a V.4b side effect.

### Codes longer than `CODE_LENGTH` are accepted — left to #30

- **Status:** Deferred to **#30** (code-validation fixes), pinned meanwhile by a characterization test

- **Context:** found while fixing a hollow fast-check property in V.1's review: `validateGameCode`
