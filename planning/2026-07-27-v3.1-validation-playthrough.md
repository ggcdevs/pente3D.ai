# v3.1 validation playthrough

**What this is for.** Eight tickets describe bugs that v3.1 claims to have fixed. Each one was found
by you, playing — not by a test — so each one gets confirmed the same way before it closes. Then a
second part asks you the questions I genuinely cannot answer from the code: copy, policy, and one
probe whose result decides whether a ticket survives at all.

**Time:** Part 1 is one sitting, maybe 20–30 minutes. Part 2 you can do in the same session.

---

## Before you start

Two devices — phone and laptop. Both at **https://ggcdevs.github.io/pente3D.ai/dev/**.

Confirm they're on the same build before anything else, because a build mismatch would invalidate
every result below (and is itself the subject of Q4):

```bash
curl -s https://ggcdevs.github.io/pente3D.ai/dev/version.json
```

A few checks want the console. On the laptop, `__pente` is the probe surface — everything below uses
these:

| Probe | Tells you |
|---|---|
| `__pente.getNetGameUuid()` | which *game* you are in (the identity that matters in v3.1) |
| `__pente.getNetSeatOwners()` | who owns white and black, by playerId |
| `__pente.getHeadHash()` | the hash chain head — two peers in sync have the same one |
| `__pente.getHistory()` | `{maxPly, viewedPly}` for the slider |
| `__pente.getState()` | board + captures + whose turn |
| `__pente.getArchive()` | the games list contents |

On the phone, if you can't get a console, every check below has a visual equivalent — I've noted it.

**Record three things per step: pass / fail / *surprised me*.** The third is the valuable one. #40,
#45 and #46 all started as "huh, that's odd" during a game, not as a failing test.

## Part 1 — the eight fixes

### 1. Two people who both tapped "Join" both got Black

*What used to happen:* colour was decided by **which button you pressed** — Host made you White, Join
made you Black. So if you and a friend both tapped Join on the same code, you were both Black, there
was no White, and nobody could move. It only worked if exactly one of you hosted.

*What should happen now:* seats are owned by your player identity and handed out first-available, so
the button you press is irrelevant.

**Do:** both devices enter the **same code**, and both choose the same entry option — **Join /
Dealer's choice**. Deliberately do *not* have one of you host.

**Expect:** you get different colours, one game, and play works.

**Console:** `__pente.getNetSeatOwners()` on both — two different playerIds, one per seat.

**If it's wrong:** both same colour, or "no one can move". That's the original bug surviving.

> Settles **#31**

---

### 2. The rematch that was secretly two different games

*What used to happen:* on a rematch each side independently created a new game, so the two of you had
**different game UUIDs** for what you thought was one game. It worked anyway because sync leaned on a
separate epoch counter — but the archive stored two records for one game, and a reconnect mid-rematch
could hit a "game mismatch" rejection.

*What should happen now:* the rematch UUID is **derived** from the previous game plus the rematch
generation, so both sides compute the same identity without having to agree on one over the wire.

**Do:** from the game in step 1, play to a finish, then **Rematch** from either side and accept on
the other.

**Expect:** colours swap on both. The board resets on both together, not one-then-the-other.

**Console — this is the actual check:** run `__pente.getNetGameUuid()` on **both** devices, before
and after the rematch.
- Before: identical to each other.
- After: a **new** value — and still **identical to each other**.

**If it's wrong:** the two devices report different UUIDs after the rematch.

> Settles **#42**

### 3. The one that bricked games: locking your phone

*This is the bug that froze v3 and is the reason v3 never shipped.* Your own report:

> i played from my phone, then locked the screen. it disconnected. i played a move on the laptop.
> after turning my phone back on, it reconnected, but it never got an update. so it was never able to
> play because it thought it was still the laptop's turn. to try and trigger some network refresh, i
> clicked "Undo" — that threw an error that their states had diverged, and the game was no longer
> playable.

*Why it happened:* the socket died, the MQTT client silently reconnected and re-subscribed — but
nothing re-ran admission, so no state was exchanged. The move made while you were away had been
published non-retained, so it was simply *gone*. Your session never noticed anything had happened.

*What should happen now:* when a peer appears live, whoever is resident in the room **republishes**
the current game unprompted. The trigger is any fresh live presence, not an absent→present edge —
because a blip the broker never turns into an absence produces no edge to fire on.

**Do:** mid-game, **lock the phone**. Play a move on the laptop. Wait a few seconds. **Unlock** the
phone.

**Expect:** the phone catches up **on its own** — the laptop's move appears, and it is correctly the
phone's turn. No button pressed, no refresh.

**Console (phone if you can, else compare boards):** `__pente.getHeadHash()` matches on both.

**Then push it further:** play the phone's move. It should be accepted.

**If it's wrong:** the phone sits at the old ply, thinks it's the opponent's turn, and can't move.

> Settles **#45** · already proven mechanically by `npm run scenario:issue45` over the live relay,
> but this is the flow you actually reported, so it's worth doing by hand.

### 4. Reusing a code resurrected an old board — and pushed it at your opponent

*What used to happen, two ways.* Locally: a game was persisted **per room code**, so typing `TESTTT`
again brought back whatever board `TESTTT` had last time, even when you asked for a New Game. Over
the network it was worse — your report:

> joined TESTTT from my phone with a new game → blank networked game, waiting for opponent. then I
> joined from my laptop (which associates TESTTT with some old game), New Game, Enter. It changed the
> board **for both my phone and the laptop** to the board my laptop had saved for TESTTT. i had to
> totally wipe my laptop localStorage.

*What should happen now:* the per-code record is deleted outright — a code is pure rendezvous and
identifies no game. And the seed you pick is **enforced on the wire**: New sends and accepts only
empty state; Dealer's choice is the only kind that will adopt a non-empty game from a peer.

**Do:** at the **same code you've been using all along** (it now has history), start a **New Game**
from one device, then enter from the other, also choosing **New Game**.

**Expect:** an empty board on both. Not the previous game, on either side.

**Then the nastier half:** repeat, but this time have the device that has played the most games at
that code be the *second* one to enter. It must not push its old board onto the peer.

**If it's wrong:** an old board appears — on either device.

> Settles **#43** and **#46**

### 5. Rematch, swap colours, drop, come back — and deadlock

*What used to happen:* the rematch swaps your colours. But the reconnect path read a **stale** seat
map that still described the pre-swap game, so the returning player was handed their *old* colour.
Both players ended up the same colour and nobody could move. Your report ended "no one can move :p".

*What should happen now:* seats are a property of the live game, so reclaiming is against the current
one.

**Do:** finish a game → rematch → note **which device changed colour** → drop *that* device (lock it,
or airplane mode for ~10 seconds) → bring it back.

**Expect:** it returns as its **post-swap** colour. Two different colours between you. Play continues.

**Console:** `__pente.getNetSeatOwners()` on both — should agree about who owns what.

**If it's wrong:** both devices show the same colour, or the turn indicator never lets either of you
move.

> Settles **#40**

### 6. The games list is now load-bearing, not a nicety

*What changed and why it matters:* in v3.1 a reload deliberately lands on an **empty slate** — no
auto-loading a game from storage, because auto-loading a code-keyed game is exactly what caused
#43/#46. The consequence is that **the games list is the only route back to a game**. If it's broken,
games are unreachable, which is a much bigger deal than the ticket that requested it implies.

**Do:**
1. **Reload** the laptop tab mid-game. You should get an empty board, then a **prompt** offering to
   rejoin, naming your colour.
2. Answer **No** — deliberately decline.
3. Open the **games list**. Find that game. **Resume** it.

**Expect:** the list shows every game from this session, finished vs unfinished distinguished, and
Resume puts you back into the unfinished one, in the right seat, with the right board.

**Console:** `__pente.getArchive()` — one record per game, not one per move.

**If it's wrong:** a game you played is not listed, or Resume lands you somewhere unexpected.

> Settles **#37** · also exercises the empty-slate/breadcrumb behaviour that is v3.1's core

### 7. Divergence resolution — the one you can't test by playing

*Why not:* two correct clients **cannot** diverge. The turn gate caps legitimate drift at exactly one
move, and one move is auto-fast-forwarded. To see the resolution flow you need a client that behaves
badly, which is what the CLI's `local-undo` simulates.

*What it should do:* when histories genuinely fork, both sides see a panel describing what each side
did after the last shared move, and offer three ways out — continue from mine, continue from theirs,
or both rewind to the last shared move. Whichever you agree on is **replay-validated through the
rules engine** before it's adopted, so a peer can't hand you an illegal history.

**Do:** from the repo root —

```bash
npm run scenario:divergence
```

No setup needed; the Node relay config falls back to the live broker.

**Expect:** exit 0. (Exit 2 means it skipped for want of a relay — that's not a pass. Exit 1 means
the flow is broken.)

**Then, for the copy — see Q2 below**, because the panel's wording is one of the things deliberately
left plain for you.

> Settles **#38**

These eleven tickets I closed on the evidence in the tree; this is a glance, not a gate. Anything
that looks wrong, say so and I'll reopen it.

On the **phone**, in one pass:

- The menu is a **hamburger drawer**, and you can **orbit the board while it's open** — that was the

- Change a colour in settings → the board updates **without a reload**.
- The score banner reads `White: 0 · Black: 0`, not `White: 0Black: 0`.

## Part 2 — questions I need you to answer

These are the ones where the code can tell me *what happens* but not *what should*.

### Q1 — Does the history slider actually work in a networked game? (decides #33)

**Context.** There are two tickets here and they're easy to confuse. One asked that scrubbing history
in a networked game stays **purely local** — no network traffic, no touching the shared game. That's
satisfied and permanently locked by a test, and I closed it. The *other* one, still open, reports
that the slider isn't merely local — it's **inert**. In v3 the scene rendered the session's game
while the slider read a *different*, scene-local game that was never advanced during networked play,
so there was no history to scrub and the control sat disabled.

v3.1 restructured exactly that relationship, but nobody has re-checked the symptom. The slider still
reads `scene.getHistory()`, so it may have fixed itself, or not.

**Do:** in a networked game with several moves played, drag the history slider back. Then:

```js
__pente.getHistory()
```

**Tell me:** is the control **enabled**? Does the board actually change as you drag? And what does
`getHistory()` report — is `maxPly` the real move count, or 0?

**Why it matters:** if it scrubs, #33 closes now. If it's still inert, #33 needs re-specifying against
the new model before anyone builds it — and specifically I'd need to know what *you* want scrubbing a
networked game to mean: purely a local review that snaps back to live, or something the opponent can
see you doing.

### Q2 — The divergence panel's wording (a deliberate collaboration point)

**Context.** When histories fork, both players get a panel. It was written **plain on purpose** and
flagged as wanting your voice. The design rule it follows: it must read like a *game* event, not like
a git merge conflict — so there are no hashes, no "ours/theirs", no ply arithmetic. Each option says
in one sentence what it **keeps** and what it **drops**. The three options are: continue from your
history, continue from theirs, or both rewind to the last move you shared.

The copy lives in a pure model with its own tests specifically so it can be tuned freely.

**Do:** run `npm run scenario:divergence` and read what it prints, or drive it by hand with
`pente local-undo` to see the panel in the browser.

**Tell me:** does it read like something you'd want to see mid-game with a friend? Rewrite any line
you don't like — I'll wire your wording in.

### Q4 — Version mismatch: warn, or refuse? (decides #51's scope)

**Context.** v3.0 and v3.1 clients **cannot** play together — the wire semantics changed (seed
proposals, admission payload, republish, reconciliation). And every branch deploys to its own
subpath, so it is genuinely easy for two people to land on different builds: you on `/dev/`, a friend
on a cached tab of the root. Today that fails confusingly, or misbehaves silently, rather than saying
why.

The app already knows its own version — it's on `window.__penteVersion` — but it is **displayed
nowhere in the UI**, and it isn't exchanged in the handshake.

**Do:** deliberately mismatch. Phone on `/dev/` (v3.1), laptop on `/test/` (still v3). Same code. Try
to play.

**Tell me:** what did it look like? And then the policy call — when builds differ, should the app
**warn and let you try anyway**, or **refuse to connect**? My suggestion is to track a separate small
wire-protocol number that only changes when the protocol actually changes, so a cosmetic patch
release never blocks a game but a real protocol change does. But the answer partly depends on how bad
the failure you just watched looks.

*Note:* the ticket's own argument for doing this now — "the handshake is being rebuilt anyway, cheap
now, awkward later" — has expired; the rebuild is done. The counter-argument got stronger though: the
moment v3.1 hits `main`, friends on cached v3.0 tabs are a real scenario.

### Q5 — Colour preference when starting a new game (decides #49's timing)

**Context.** When you *rejoin* a game, your colour is derived from the game itself and simply
displayed — never negotiated. That's what keeps #31 and #40 fixed, and it isn't up for discussion.
But for a genuinely **new** game, letting someone say "I'd like White" is a nice touch. It would be a
**preference, not a claim** — if you both want White, the existing initiator election (earlier
arrival, then lower playerId) decides and the loser takes the other seat.

It's listed as remaining-before-promotion, but it is new scope on a release that's otherwise ready.

**Do:** step 4 above already has you both choosing New Game at the same code.

**Tell me:** did you care what colour you got? If yes, I'd build it before promotion; if not, it moves
to the next milestone and v3.1 ships as-is.

### Q6 — Long game codes are accepted (decides how #30 gets rewritten)

**Context.** This ticket is mislabelled as done, and its body describes a bug that *is* fixed while
hiding one that isn't. The filed complaint — `TEST12` rejected with a misleading "letters and numbers
only" message — is fixed; your 2026-07-23 decision (full `A-Z`+`0-9` everywhere, uppercase-normalise,
no ambiguity exclusions) is implemented, message and all.

What's left: the validator checks a code isn't **too short**, but never that it's **too long**. So an
8-character code validates and is used. It's recorded as a knowingly-shipped limitation.

**Do:** type `TESTTT12` as a custom code on one device and a *different* long code on the other,
e.g. `TESTTT99`.

**Tell me:** does anything worse than "it's accepted" happen — in particular, do the two devices end
up in **different rooms** while both appearing to have joined successfully? That's the difference
between "cosmetic, add a `too-long` check" and "actually confusing, fix properly".
